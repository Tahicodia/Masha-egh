# ЛР №14, варіант 3 «Посилка+»: сценарій здачі

## Вступ
«Було дві ситуації. Зміна статусу, про яку мають дізнатися багато незалежних отримувачів, це **Observer**. Пристрої сортувального центру, що викликають один одного напряму, це **Mediator**.»

## Завдання 1. Observer (статус відправлення)
**Проблема.** Код зміни статусу напряму викликав відправника, отримувача, бухгалтерію; підключення API магазинів вимагало правок у цьому коді.
**Рішення.** `Shipment` (Subject) тримає список `StatusObserver` і при `changeStatus` сповіщає всіх. Конкретні отримувачі (`Sender`, `Receiver`, `Accounting`, `OnlineShop`) самі вирішують, як реагувати. Підписка й відписка працюють у runtime.
**Що відкривати:**
1. Діаграму `task1_observer`: `Shipment` → `StatusObserver` з кратністю `0..*`, чотири реалізації.
2. `Shipment.java`: `subscribe`, `unsubscribe`, `changeStatus` (копія списку).
3. `Accounting.java`: умовна реакція лише на «вручено».
4. `Main.task1Observer()`.
5. Лог: крок 1 (бухгалтерія ігнорує «в дорозі»), крок 2 (бухгалтерія фіксує 450 грн, магазин реагує), крок 3 (отримувач більше не отримує).
**Що сказати.** «Підключення нового отримувача це один новий клас і один `subscribe`, `Shipment` не змінюється.»

## Завдання 2. Mediator (сортувальний центр)
**Проблема.** Стрічка, сканер, ваги, сортувальник і зона завантаження викликали методи один одного; заміна сканера вимагала змін у трьох класах.
**Рішення.** Пристрої (Colleague) знають лише `SortingMediator` і повідомляють про події через `report()`. `SortingCenter` (ConcreteMediator) містить усі правила: зважування → сканування → сортування → завантаження, зупинка при перевантаженні, відкладення при відсутності машини.
**Що відкривати:**
1. Діаграму `task2_mediator`: `SortingMediator`, `SortingCenter`, `SortingDevice` і п'ять пристроїв.
2. `SortingCenter.onEvent`: `switch` по подіях з усіма правилами.
3. Будь-який пристрій, наприклад `BarcodeScanner.java`: він не знає про сортувальника.
4. `Main.task2Mediator()`.
5. Лог: ланцюжок `Сканер → Координатор → Сортувальник`, зупинка стрічки на 80 кг, «завантаження НЕ дозволено», після подачі машини «завантаження почалося».
**Що сказати.** «Заміна сканера не торкається ваг, сортувальника чи стрічки: змінюється один клас.»

## Питання, які можуть поставити
| Питання | Відповідь |
|---|---|
| Чим Observer відрізняється від Mediator? | Observer: один відправник, багато незалежних отримувачів, зв'язок «один до багатьох». Mediator: багато рівноправних учасників, зв'язок «усі з усіма» замінено на «усі з посередником» |
| Навіщо копія списку в `changeStatus`? | Підписник може відписатися під час сповіщення; без копії буде `ConcurrentModificationException` |
| Недолік Mediator? | Координатор може стати «божественним об'єктом» |
| Чому ваги не зупиняють стрічку самі? | Правило «що робити при перевантаженні» належить координатору; ваги лише вимірюють |
| Push чи pull у Observer? | Змішане: передаються старий і новий статус, а решту отримувач бере з `Shipment` |
| Ризик Observer? | Забута відписка тримає об'єкт у пам'яті |
