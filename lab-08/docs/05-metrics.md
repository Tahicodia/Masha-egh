# Завдання 5. Метричний аналіз (Low Coupling + High Cohesion)

Усі числа отримано скриптом `docs/metrics/compute_metrics.py` (повний вивід — `docs/metrics/results.md`):

```bash
python3 docs/metrics/compute_metrics.py
```

## 1. Угоди підрахунку

* **CBO** — кількість *інших* типів проєкту, явно названих у коді класу: поле, параметр, повернення,
  локальна змінна, `new`, статичний виклик, `implements`/`extends`, `catch`/`throws`. Типи `java.*` та примітиви не рахуються.
* **LCOM4** — вершини: нестатичні методи, крім конструкторів і тривіальних акцесорів; ребро: спільне поле або прямий виклик.
  `1*` означає, що після виключення акцесорів методів не лишилось (незмінний носій даних) — вважаємо ідеально згуртованим.
* **Instability** `I = Ce / (Ca + Ce)` — на рівні пакетів; composition root `Main` виключено.

## 4. Instability шарів (Stable Dependencies Principle)

| Пакет | Ca | Ce | I (Task4) |
|---|---|---|---|
| `domain` | 11 | 0 | **0.00** |
| `application` | 8 | 5 | **0.38** |
| `ui` | 0 | 3 | **1.00** |
| `infrastructure` | 0 | 8 | **1.00** |

`I(ui) = 1.00 → I(application) = 0.38 → I(domain) = 0.00`: залежності спрямовані від нестабільного до стабільного ✔.
Інфраструктура залежить від `application` та `domain` (а не навпаки) — це Dependency Inversion через порти.

## 5. Висновки та чесні застереження

1. **Цільові значення досягнуто:** для всіх сутностей і контролера CBO ≤ 4 (максимум = 4: `SubscriptionController`, `Subscription`, `PlanType`); LCOM4 = 1 для всіх класів з логікою.
2. **CBO в абсолютних числах не впав** (3 → 4 для головного класу). Причина: вихідний клас був маленьким і зв'язувався з трьома пасивними структурами. Покращилась *якість* зчеплення: замість 43 прямих звернень до чужих полів — виклики через методи й інтерфейси (data coupling → contract coupling). Саме це треба наводити на захисті.
3. **LCOM4 Legacy = 1 — хибнопозитивний результат** метрики (один метод ⇒ один компонент). Реальна проблема Legacy видна лише через кількість відповідальностей (9) і цикломатичну складність.
4. **Транзитний тип у контролері.** `Subscription` проходить через `SubscriptionController` як результат `factory.create(...)` та аргумент `repository.save(...)`, але в його коді не названий (однорядковий вираз без локальної змінної). За прийнятою угодою CBO = 4; інструменти, що аналізують байт-код (напр. CK), можуть додати цей тип і показати 5. Для захисту слід уточнити, яку угоду використано.
5. **`SubscriptionFactory` має CBO = 6 (Task4)** — це Creator-збирач, що з'єднує команду, репозиторій клієнтів, каталог тарифів, політику знижки та домен. Норматив ≤ 4 стосується сутностей і контролерів, тому формально порушення немає, але при зростанні вимог її варто розділити (напр. винести вибір послуг).
6. `Main` (CBO = 11–12) — composition root, єдине місце, що знає всі реалізації; це свідомий компроміс Protected Variations, у метриках шарів не враховується.
